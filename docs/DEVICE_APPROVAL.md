# 자료실 기기 승인 · WebAuthn 학습용 구현

제공 엔진의 기기 승인 API 계약은 이 프로젝트에 없습니다. 이번 구현은 그 계약을 추측한 연동이 아니라, 자료실 자체의 **별도 학습용 승인 흐름**입니다. 기존 판정기의 `deviceRegistered` 입력 계약·규칙·로그인 도우미는 변경하지 않습니다. 제공 엔진의 기기 등록·회수와 자동 동기화되거나 심판이 이 경로를 지원한다고 주장하지 않습니다.

## 준비와 실행 순서

1. 저장소 소유자가 `sql/step11-devices.sql`을 검토한 뒤 해당 학습 Supabase 프로젝트의 **SQL Editor → Run**으로 실행합니다. 새 테이블 세 개만 만들고 기존 메모·공지·감사·권한 정책은 수정하지 않습니다. 테이블이 이미 있으면 CREATE가 실패하며 덮어쓰지 않습니다. RLS를 켜고 PUBLIC·anon·authenticated의 직접 권한은 회수하며 service_role만 사용합니다. 새 키를 보내거나 만들 필요는 없습니다. 서버의 기존 `SUPABASE_URL`·`SUPABASE_SECRET_KEY`를 그대로 사용합니다.
2. 변경을 배포한 뒤 기존 계정으로 로그인합니다. 아직 기기 증명이 없으므로 메모 조회 요청을 보내지 않고 편집기도 숨깁니다. **기기 승인 요청**을 누르면 브라우저/운영체제의 기본 WebAuthn 사용자 확인이 열립니다. 취소·미지원·검증 실패는 자료 없이 닫힙니다. 별도 프로그램을 설치하지 않습니다.
3. 서버가 등록 응답의 origin·RP ID·일회용 challenge·사용자 확인을 SDK로 검증하면 DB에 **pending** 요청 하나를 만듭니다. 화면에는 **대기 중**과 승인 요청 UUID만 보입니다. 버튼이나 요청 본문으로 approved·owner·role을 정할 수 없습니다.
4. 저장소 소유자가 Supabase **SQL Editor**에서 SQL 파일 끝의 조회문으로 요청 UUID·계정·시각을 비공개로 대조합니다. 자신이 실제로 진행한 요청임을 확인한 뒤, 주석의 정확한 UUID·소유자 조건을 넣은 UPDATE 한 건만 별도로 실행해 승인합니다. 전체 요청을 승인하는 SQL이나 웹 승인 API는 없습니다. 강사에게 자료·승인·키를 요구하지 않습니다.
5. 같은 로그인 창에서 **이 기기 확인 / 결과 조회**를 누릅니다. 등록 때의 기기 증명 세션이 만료됐다면 같은 인증 장치의 WebAuthn 서명을 다시 확인합니다. 서버가 현재 로그인에 묶인 증명 세션과 DB의 approved 상태를 모두 확인한 경우에만 메모 목록·편집기를 엽니다. A/B 각각 필요한 기기 요청을 따로 확인합니다.
6. 승인된 기기에서 기존 자기 메모 조회·추가·수정·삭제·로그아웃을 다시 확인합니다. 미승인 창은 자료가 없고 직접 메모 API도 403 `DEVICE_NOT_REGISTERED`여야 합니다. 다른 계정·다른 로그인 토큰으로 증명 쿠키를 옮겨도 열리지 않아야 하며, 승인 기기에서도 기존 타인 메모 접근·소유자 변경은 거부되어야 합니다. 임시 가상 메모로만 변경 시험을 합니다.

**SQL 적용·실제 승인·실기기 WebAuthn·새 배포는 아직 미실행입니다.** 이 준비 없이 배포하면 기존 계정도 메모를 열 수 없습니다. 로그인은 가능하지만 기기 증명이 없으면 자료 API는 거부합니다. 제공 심판의 Bearer 요청에도 기기 검사 우회 예외가 없으므로, 그 요청에 이 별도 기기 증명을 연결하지 않은 상태를 이전 심판 정상 요청까지 유지됐다고 표현하지 않습니다.

## 서버 경로와 신뢰 경계

| 메서드·경로 | 동작 |
| --- | --- |
| GET `/api/device-status` | 현재 로그인에 묶인 HttpOnly 증명 쿠키와 DB 상태를 확인. 키·메모를 반환하지 않음 |
| POST `/api/device-registration-options` | 2분 유효·로그인에 묶인 일회용 등록 challenge 발급 |
| POST `/api/device-registration` | 정확한 `{challengeId,credential}` 응답을 검증하고 pending만 생성 |
| POST `/api/device-authentication-options` | 해당 로그인 소유자의 pending/approved 자격 증명만 확인 대상으로 제시 |
| POST `/api/device-authentication` | origin·RP ID·challenge·서명·사용자 확인·counter를 검증하고 증명 세션 발급 |

options POST 본문은 `{}`입니다. 경로 자체로 기능을 선택하며 쿼리로 역할·기능·기기를 선택하지 않습니다. 기기 응답은 `{status,deviceRegistered,requestId?}`이며 requestId는 요청 UUID입니다. 기기 승인 API에서 메모·토큰·서버 키·개인키·공개키를 결과/로그로 내보내지 않습니다. WebAuthn options/credential 전송에는 프로토콜상 공개 challenge·공개 자격 증명 정보가 필요하며 이를 인증 장치 개인키와 혼동하지 않습니다.

서버는 SimpleWebAuthn 공식 SDK의 [등록·서명 확인 흐름](https://simplewebauthn.dev/docs/packages/server)을 사용합니다. 인증 장치 개인키를 코드에서 생성·추출하거나 localStorage·sessionStorage·IndexedDB에 보관하지 않습니다. 서버 DB에는 자격 증명 ID·공개키·counter만 둡니다. 플랫폼 인증 장치와 사용자 확인을 요청하고, SDK가 singleDevice·백업되지 않음으로 확인한 자격 증명만 받습니다. 동기화되는 passkey만 지원하는 환경은 거부될 수 있습니다. 이를 우회해 동기화 키를 등록 기기로 처리하지 않습니다. `attestation: none`이므로 제조사 하드웨어 인증이나 물리 기기 복제 불가능성을 증명하는 구현은 아닙니다.

`__Host-vault-device`는 개인키가 아닌 **10분짜리 기기 증명 세션**이며 Secure·HttpOnly·SameSite=Strict·Path=/ 쿠키입니다. 원문을 JS나 JSON에 전달하지 않고 DB에는 SHA-256만 저장합니다. 쿠키는 검증된 로그인 토큰에 묶여 다른 로그인·다른 계정에서는 유효하지 않습니다. 메모·공지·복구 API가 매번 DB 승인 상태·만료·소유자를 다시 확인합니다. DB에서 회수하면 다음 보호 요청부터 거부됩니다. 로그인 변경·갱신·로그아웃에서 기존 증명 세션을 회수하고 쿠키를 지우므로 필요하면 **이 기기 확인 / 결과 조회**를 다시 누릅니다. 기기 증명 쿠키도 단기 세션인 만큼 탈취 위험이 전혀 없다고 주장하지 않습니다.

승인·DB·네트워크 확인 실패, 늦게 도착한 승인 응답, 로그인 변경에서는 화면의 메모·편집 초안을 지웁니다. 설치 표시·클라이언트 userId/role·deviceRegistered·브라우저 메뉴는 권한을 부여하지 않습니다. 실제 요청 중 발생하는 회수와 DB 쓰기의 완전한 동시성까지 보장하는 운영 트랜잭션으로 주장하지 않습니다.

## 시험과 기록

재실행: `node --test test/device.test.mjs test/device-client.test.mjs test/auth-ui.test.mjs test/notes.test.mjs`.

가상 인증 장치의 키는 시험 프로세스 메모리에만 생성하고 저장·출력하지 않습니다. 실제 SDK로 등록/서명을 검증하며 DB는 모의 구현입니다. 대기 상태 거부, 별도 DB 승인 뒤 기존 CRUD, 잘못된 origin·서명·사용자 확인·재사용 challenge·다른 계정/로그인·만료·회수·로그아웃 거부, 공개/비밀 키 노출 방지를 확인합니다. 기존 API 회귀 시험은 명시적인 승인 기기 fixture를 제공하며 운영 코드에 시험용 우회 옵션은 없습니다.

현 상태의 전체 로컬 시험 124개는 통과했습니다. 이것은 실제 Windows Hello·학습 DB 적용·제공 엔진·심판 통과의 증거가 아닙니다. 이전 실제 정상 사용 보고와 새 기기 승인 뒤 실측을 섞지 않습니다. SQL 실행·실기기 등록/승인·배포 뒤 A/B 재검증은 미실행으로 남깁니다.
