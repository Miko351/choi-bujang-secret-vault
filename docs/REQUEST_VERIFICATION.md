# 1~11단계 요청 실측표를 만드는 절차

이 문서는 정상 허용·금지 요청 거부를 **같은 배포의 실제 응답**으로 남기는 절차와 빈 점검표입니다. 이번 작성에서는 요청을 보내지 않았으며 아래 **41행은 모두 미실행**입니다. 저장소에 제공 심판의 공식 41종 명단은 없어, 기존 1~11단계 요구와 구현한 경로를 기준으로 만든 **프로젝트 자체 점검표**입니다. 공식 41종과 같거나 심판을 통과했다고 주장하지 않습니다. 공식 명단을 확보하면 항목별로 대조하고 대응하지 않는 시험은 완료 수에 넣지 않습니다.

## 1. 배포와 시험 대상을 고정

1. 실행할 때마다 이 문서를 `local-only/`의 별도 파일로 복사하고 실행 묶음 이름·실제 배포 주소·Git 커밋을 적습니다. 기존 기록은 덮어쓰지 않습니다. 아래 결과 칸은 먼저 전부 미실행으로 둡니다. 확인 전 과거 README의 성공 보고·제출 묶음·모의 시험 출력을 복사하지 않습니다.
2. `/aleph.json`의 저장소·단계·커밋이 이번 시험의 배포와 맞는지 확인합니다. 다르면 해당 조회 결과는 그대로 남기고 나머지 시험을 이 커밋의 결과로 묶지 않습니다. 과거 1단계의 공개 자료나 3단계의 소유자 검사 부재를 다시 열지 않고 **현재 완성된 보호 상태**를 검사합니다.
3. 현재 정상 자료 요청은 **로그인 + 앱 자체의 승인 기기 증명**이 필요합니다. 11단계 SQL·A/B 각각의 실제 기기 승인 준비가 없으면 정상 자료 시험은 미실행입니다. 금지 요청의 403만으로 전체 통과라고 쓰지 않습니다. 제공 엔진의 기기 등록과 앱의 WebAuthn 승인은 별도이며 연결되지 않은 엔진 시험은 미실행입니다.
4. A/B는 별도 브라우저 프로필/창을 사용하고 무로그인은 새 시크릿 창으로 구분합니다. 정상 CRUD에는 새 임시 가상 메모만 씁니다. A→B 교차 접근용 A 시험 메모는 CRUD 삭제용과 **별도**로 준비하고 A의 정상 한 건 GET으로 존재를 확인한 뒤 B의 금지 요청을 보냅니다. B의 자기 메모 정상 요청도 먼저 확인합니다. 지워진/없는 UUID의 404를 타인 접근 거부로 계산하지 않습니다.
5. 본문·비밀번호·토큰·키·실명·원본 사용자/기기 ID·전체 HAR는 기록하지 않습니다. URL은 표의 경로 모양과 `A-임시`, `B-임시`, `B-복구대상` 같은 시험 별칭으로 표시합니다. 실제 대상과 별칭의 대응이 필요하면 비공개 환경에서만 확인합니다. 다른 사람 자료·기존 복구 대상 원본을 훼손하거나 운영 정책을 침해 상태로 바꾸지 않습니다.

실행 묶음: **미정** / 배포 주소: **미확인** / 배포 커밋: **미확인** / 실제 실행 수: **0/41** / 허용 실측: **0** / 거부 실측: **0**. 이 숫자는 이번 빈 점검표의 기록 수이며 서비스에 사건이 0건 있었다는 뜻이 아닙니다.

## 2. 요청 하나를 보내고 같은 응답의 메타데이터만 채우기

1. 개발자 도구 **Network → Preserve log**를 켜고 해당 시험 동작 하나를 실행합니다. **Name → Headers/Response**에서 실제 메서드·경로·상태·Content-Type·안전한 오류 코드 또는 응답 형태만 읽습니다. 성공 메모 본문과 비밀번호·쿠키·Authorization을 표로 복사하지 않습니다. 변경 요청은 시험 계정의 임시 메모에만 보내며 필요하면 브라우저 개발자 도구의 요청 편집 기능을 사용합니다. 실제 승인 절차나 인증서/키를 흉내 내는 curl 헤더를 만들지 않습니다.
2. **실제 API 결과**에는 HTTP 상태와 JSON 오류 코드 또는 안전한 형태/개수만 적습니다. 정상 GET은 본문을 읽어 본인 자료임을 비공개로 확인한 뒤 `{id,title,body} 한 건`·`본인 배열`처럼 기록합니다. 금지 요청은 응답에 자료가 없고 기대한 거부 사유인지 확인합니다. HTML 오류·일반 404·서버 설정 실패를 인증/소유자 검사 통과로 대신하지 않습니다.
3. **요청 ID(출처)**는 같은 응답에 실제 존재하는 서버 추적 ID만 적습니다. HTTP는 `x-vercel-id` 또는 서버 계약이 보장하는 `x-request-id`의 헤더 이름과 값을, 엔진 판정은 요청과 응답이 일치하는 계약상의 `requestId`를 적습니다. 직접 만든 T01 같은 시험 번호·커밋·클라이언트가 보낸 값을 서버 추적 ID로 바꾸지 않습니다. **기기 API의 `requestId`는 승인 기록 UUID이며 호출 추적 ID가 아닙니다.** 추적 ID가 제공되지 않으면 `미제공 / 추적 대조 불가`로 적고 상관관계 확인은 보류합니다. 키·세션 토큰을 ID 대신 쓰지 않습니다.
4. **확인 시각**은 그 응답을 확인한 즉시 UTC ISO 형식으로 기록합니다. 터미널 명령 `node -p "new Date().toISOString()"`으로 확인할 수 있습니다. 문서 작성 시각·커밋 시각·요청 본문의 `at`·다른 요청의 `observedAt`을 재사용하지 않습니다. 응답 Date가 필요하면 별도로 출처를 적고 확인 시각과 혼동하지 않습니다. 미실행 행에는 시각을 넣지 않습니다.
5. **판정**은 기대와 실제 응답·자료 범위·변경 보존 여부·추적 근거를 대조한 뒤에만 `허용 확인` 또는 `거부 확인`으로 바꿉니다. 기대와 다르면 `실패`, 응답은 왔지만 원인/범위/추적 대조가 안 되면 `확인 보류`, 요청을 못 보냈으면 `미실행`과 이유를 적습니다. 예를 들어 B 요청이 미승인 기기 403에서 막혔다면 타인 메모 404 시험의 통과로 세지 않습니다.
6. 같은 시험을 다시 실행하면 별도 실행 묶음을 만들거나 시도별 행을 추가해 원래 실패/미실행을 보존합니다. 한 시험에 여러 요청이 필요한 경우 `options`, `검증`, `추가`, `읽기` 같은 순번별로 **실제 결과·추적 ID·확인 시각을 각각** 대응시킵니다. 모두 실측하기 전에는 묶음 시험을 완료로 표시하지 않습니다. 41은 시험 종류 수이고 실제 HTTP 요청 수와 같지 않습니다.
