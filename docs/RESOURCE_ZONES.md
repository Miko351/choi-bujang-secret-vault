# 8단계 서버 관리 구역 정책

현재 구역 규칙의 식별 이름은 `resource_scope`입니다. `RULE_IDS`와 실제 판정 응답의 `ruleIds`에 같은 이름을 사용하며 이전 `resource_zone` 이름은 기록에만 남깁니다. v1 요청에는 검증된 강사 역할이 없으므로 판정기는 공지 쓰기(POST·PUT·PATCH·DELETE)를 누구에게나 거부합니다. 서버 편집자 정책이나 재확인 완료도 이 거부를 우회하지 못합니다.

메모 API의 일반 Supabase 소유자는 검증된 사용자 UUID 그대로입니다. 검증된 심판의 가상 소유자는 발급자·앱·실행·A/B 신원·사용자 번호를 묶은 내부 UUID이며, 서명 검증이 완료된 뒤에만 결정합니다. 로그인 도우미나 엔진 요청 계약은 변경하지 않습니다. 이 구분으로 같은 `sub`라도 다른 심판 신원·실행의 메모는 접근할 수 없습니다. 기존 학생 메모·DB 행은 자동 수정하지 않습니다.

강사에게 계정·키·계약 파일을 요청하지 않습니다. 브라우저 메뉴나 요청의 `role`로 권한을 만들지 않습니다. 서버 관리자가 승인한 자료별 접근 기록을 서버 환경변수 `VAULT_ZONE_POLICY`에서 읽습니다. 공개 화면 코드에 이 변수를 복사하지 않습니다. 현재 실제 정책을 설정하거나 학습 DB를 변경하지 않았습니다.

환경변수 JSON 형식은 다음과 같습니다. 빈 배열은 권한을 부여하지 않습니다.

```json
{
  "version": 1,
  "noteOwners": [],
  "noticeEditors": [],
  "apiNoticeEditors": []
}
```

- `noteOwners` 항목: `{classId, projectId, subjectId, id}`. 서버가 관리하는 메모 소유자 기록입니다. `id`는 메모의 소문자 UUID이며 나머지는 엔진이 확인한 범위와 가명 주체입니다. 동일 반·프로젝트·자료 ID에 소유자가 두 건 있으면 정책 전체를 거부합니다.
- `noticeEditors` 항목: `{classId, projectId, subjectId, id}`. 기존 정책 형식과의 호환을 위해 유지하지만 v1 판정기의 공지 쓰기 권한을 부여하지 않습니다. 엔진의 강사 역할이라는 새 요청 항목을 만들지 않습니다.
- `apiNoticeEditors` 항목: `{userId, id}`. 변경하지 않은 로그인 도우미가 검증한 Supabase 사용자 UUID에 지정 공지 UUID의 수정 권한을 부여하는 서버 승인 기록입니다. API는 이 권한에 더해 DB의 기존 행과 수정 후 행의 `owner_id`도 확인합니다.

엔진의 `subjectId`와 Supabase UUID를 같다고 가정하지 않습니다. 정책에는 확인된 값만 등록하며 현재 저장소에는 실제 엔진 주체와 DB 소유자를 연결한 자료가 없습니다. 임의 문자열·이메일·브라우저 헤더에서 연결을 추측하거나, 처음 요청한 사람을 자동 소유자로 등록하지 않습니다. 로컬 시험은 가상 소유자 기록을 메모리에 넣어 로직을 확인합니다. 이는 실제 정책 등록이나 운영 엔진 연결의 증거가 아닙니다.

정책 누락·잘못된 형식·알 수 없는 소유자는 UUID 메모의 GET·PUT과 공지 PUT을 거부합니다. 이전 6~7단계 연습의 `/notes/demo`는 기존 가상 소유자 범위(`class_fixture`, `project_fixture`, `learner_fixture`)의 GET만 허용하며 사용자·반·프로젝트를 바꾸면 거부합니다. 이 가상 범위를 실제 Supabase 계정의 연결 정보로 해석하지 않습니다. 판정기는 소유한 한 건을 식별하지 않는 `GET /notes`·`GET /api/notes` 전체 목록 경로를 거부합니다. 화면의 기존 메모 목록 API는 변경하지 않았고 검증된 로그인 사용자의 행만 반환합니다. 등록 기기 검사와 복합 이상 읽기 사건의 추가 확인도 유지합니다. 자료 ID는 UUID 경로로 선택하고 기능 쿼리·`export`·추가 깊이·다른 메서드·미등록 경로는 허용하지 않습니다.

공지 API는 `PUT /api/notices/:id`이며 자원 ID는 `notices`입니다. 권한이 없으면 DB 요청 전에 403 `NOTICE_EDIT_FORBIDDEN`, 로그인 없으면 401 `LOGIN_REQUIRED`를 반환합니다. 권한이 있는 요청은 `vault_notices`의 본인 소유 행만 갱신합니다. 수정 본문은 `{title,body}`, 성공 응답은 `{id}`입니다. 기존 메모 테이블·자료·URL은 변경하지 않습니다. 실제 `vault_notices` 테이블·공지 자료를 만들거나 권한 SQL을 적용하지 않았으므로 공지 수정의 실제 성공은 미실행입니다. 공지 권한을 등록하더라도 테이블이 준비되지 않으면 502 `NOTICES_UNAVAILABLE`로 거부합니다.

로컬 확인 명령:

```powershell
node --test test/decider.test.mjs test/notices.test.mjs test/notes.test.mjs
```

정상: 가상 서버 정책에 등록된 A/B의 자기 메모 읽기·수정과 기존 API의 본인 CRUD. 거부: 판정기의 전체 메모 목록·상대 메모·모든 공지 쓰기, 권한·소유자 변경 주장, 잘못된 경로, 미등록 기기, 비로그인 요청. 공지 API의 별도 서버 권한·DB 소유자 검사는 유지하며 해당 API의 모의 시험을 판정기의 공지 허용으로 해석하지 않습니다. 기존 7단계 가상 사건 확인은 `npm run decider:test`입니다.

배포 뒤 화면에서 **A 로그인 → 자기 메모 조회·수정**, **B 로그인 → 자기 메모 조회·수정**을 누르고 개발자 도구 **Network → 메모 요청 → Response Headers**의 `X-Resource-Id: notes`를 확인합니다. 직접 공지 PUT 요청은 로그인한 일반 학생에게도 자료 없는 403 JSON이어야 합니다. 공지 메뉴는 추가하지 않습니다. 이번 구현 시험에서 실제 A/B 접속·공지 DB·운영 엔진 연결은 확인하지 않았습니다. 저장점과 푸시 뒤에도 새 배포의 성공 여부는 별도로 확인합니다.
